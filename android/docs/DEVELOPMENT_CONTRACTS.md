# 앱·날씨·추천 데이터 경계 초안

M5 구현: 출퇴근·선택 성향은 [실제 저장·추천 경계](PERSONALIZATION_IMPLEMENTATION_STATUS.md)를 우선한다. 별도 앱 DataStore profile v1이며 개인 설정은 서버에 전송하지 않는다. 아래 해당 계약은 초기 초안 이력이다. 피드백·기록·자동 보정 계약은 여전히 후속 범위다.

캐시 구현: [최신 캐시 정책](CACHE_IMPLEMENTATION_STATUS.md)을 우선한다. 앱의 지역별 디스크 스냅샷과 서버의 격자별 SQLite, 실제 HTTP 시도 집계를 추가했고 수신 시각을 캐시 읽기 시 새로 쓰지 않는다.

후속 구현: [지역 기본 추천 regional-0.1](RECOMMENDATION_RULES_V0_1.md)을 앱 내부에 구현했다. 아래 개인화·출퇴근·기록 계약은 여전히 후속 초안이다. 초기 숫자 기준과 일반 참고 자료의 역할을 분리해 기록했고, 정확도나 개인화 효과를 검증한 값으로 취급하지 않는다.

후속 구현: 날씨·지역 검색의 계약 1.0은 [독립 서비스 스키마](../../weather_api/openapi.json)와 [실제 연동 결과](WEATHER_INTEGRATION_STATUS.md)를 우선한다. 아래 추천·피드백·저장 계약은 아직 초안이다. 날씨 캐시의 초기 개발 설정값과 실제 상태는 서비스 README에 기록했다.

2026-11-02. 기술 검토를 개발 단위로 옮기기 위한 계약 제안이다. 실제 API/DB 구현이나 확정 스키마가 아니다. [제품 개발 검토](PRODUCT_TECH_REVIEW.md)를 기준으로 한다.

## 앱과 서버

앱: `ViewModel → use case / recommendation engine → repository`. 공급자 JSON과 비밀 키를 ViewModel에 두지 않는다. Android의 지역 선택·날씨 표시·추천·아바타·피드백·설정을 기능별 패키지로 관리한다. 당장 다중 Gradle 모듈이나 DI 프레임워크를 추가하지 않는다.

서버: `지역/시간 요청 → 캐시 → 공급자 어댑터 → 표준 응답`. 별도 작은 날씨 경계로 시작하고 실제 공급자를 바꿔도 앱의 도메인 모델을 보존한다. 비회원 API라도 요청 제한과 입력 검증은 필요하다. 사용자 계정·신체·개인 체감 업로드는 필수로 만들지 않는다.

인증키는 서버 환경 설정으로 관리하고 앱·저장소·스크린샷·로그에 넣지 않는다. 이번 검토에서는 키를 생성하거나 읽지 않았다.

## 날씨 응답에서 필요한 구분

- `schemaVersion`, `provider`, `locationId`, `timezone`, 단위, `fetchedAt`.
- `issuedAt`: 제공자가 알려준 발표 시각. 모르면 null. 수신 시각으로 대체하지 않는다.
- `validAt`와 `periodStart/periodEnd`: 순간값·구간값을 구분한다.
- `kind`: 예보 / 관측 / 대표 관측 / 계산값. 공급자가 현재라고 부르는 모델 추정과 실측도 혼동하지 않는다.
- `freshness`: fresh / stale / unavailable, 자료 대상 범위·공급자 정책에 따른 만료 기준.
- 값의 누락은 null 또는 명시적 unavailable. 강수 없음 0과 강수 자료 누락을 구분한다.
- 강수량은 정량·범위·미만·없음·알 수 없음의 형태를 보존한다. ‘1mm 미만’을 정확히 0mm로 저장하지 않는다.
- 시각별 온도·습도·풍향·풍속·강수확률·형태·하늘 상태. UV/천문/경보는 선택적인 별도 자료 묶음으로 출처·시각을 유지한다.
- 공급자의 발표 날짜·차트 지역은 사용자별 집/직장이라는 역할과 별개다. 한 지역의 그래프에 다른 지역 값을 이어 붙이지 않는다.

필수값이 없는 구간은 ‘비교 불가/일부 자료 없음’으로 표기한다. HTTP 성공과 유효한 추천 자료 확보를 같은 상태로 처리하지 않는다. 캐시 키는 공급자·격자/지역·발표 버전·대상 범위·요청 항목을 고려한다. 실제 TTL·갱신 방식은 API 응답 확인 후 정한다.

## 추천 요청과 결과

요청에는 대상 지역·시각2개, 해당 자료 참조, 선택 민감도·생활 패턴, 보정 모델 참조를 사용한다. 프로필 미입력은 null이며 평균 신체값/보통 민감도를 입력한 것으로 저장하지 않는다.

결과에는 다음을 포함하는 안을 제안한다.

- `recommendationId`, `rulesVersion`, 생성 시각, 대상 날짜·구간.
- 실제 적용한 입력과 자료 참조, 개인 보정 버전/유효성.
- 상의·하의·겉옷의 종류·두께와 시간별 겉옷 상태(`worn`, `carried`, `none`).
- 적합한 대안 목록, 이유 코드와 그 근거. 순위 점수를 검증된 정확도 %처럼 표시하지 않는다.
- `assetKey`는 출력 표현을 위한 참조다. 추천 계산이 이미지 파일명이나 지원 자산 수에 종속되지 않도록 한다.

화면의 탐색 선택(`preview`)·오늘 후보(`candidate`)·실제 입음(`actual`)을 분리한다. 후보 선택이 편안함 피드백이나 개인 보정 이벤트가 되면 안 된다.

## 설정과 로컬 기록

설정(DataStore 후보): 지역 역할, 출발 시각·다음날 구분, 선택 요일·도보 범주·교통수단·주요 환경, 더위/추위 민감도, 알림 의도, 아바타 외형 참조. 신체 정보는 추천 기여 확인 전 수집 활성화를 보류하는 안이다.

기록(Room 후보): 추천/후보, 실제 착장과 착용 확인 여부, 경험 날짜·시각·지역, 감각 방향·강도, 활동·상황, 주관적 예보 불일치, 생성/수정 시각. 자료 스냅샷 보존은 공급자 조건에 맞춘 별도 정책으로 관리한다. 기상 API 데이터와 사용자의 체감 기록은 서로 다른 데이터다.

저장 요청은 재시도해도 같은 기록 식별자를 사용하고, 최종 성공 전 완료 화면을 표시하지 않는다. 기록 수정/삭제는 보정 기여를 갱신한다. 보정 초기화는 이전 기록을 유지하면서 그 기여를 제외하는 기준점/세대를 저장하는 안이다. 초기화 후 과거 데이터를 다시 읽어 보정을 복구하지 않는다.

## 검증 전 수치를 만들지 않을 항목

기온별 의류 기준, 바람/습도/도보의 보정량, 보정 최소 표본·상한, 개인화 효과, 캐시 만료시간·요청 예산, 알림의 갱신 보장 시간. 필요 값은 근거/버전·평가 방법과 함께 결정한다. 구조 검토 단계에서 임의의 정밀값을 코드로 고정하지 않는다.

## 첫 실제 연동에서 확인할 사항

서울 두 지역의 정상 응답, 날짜 넘김·누락·범주 강수량·갱신 지연·키 오류·한도 오류·한쪽 지역 실패를 확인한다. 공급자 실제 응답을 출처/날짜와 함께 개발 fixture로 보관할 수 있는지 이용 조건을 먼저 확인한다. 단위·시간대·격자 매핑·시점 선택을 검증한 뒤 추천에 연결한다.
