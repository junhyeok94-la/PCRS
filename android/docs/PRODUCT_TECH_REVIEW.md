# 제품 개발 검토 · 2026-11-02

후속 진행: [독립 날씨 API](../../weather_api/README.md)에 [Android 홈](HOME_IMPLEMENTATION_STATUS.md)과 [지역 기본 추천](RECOMMENDATION_IMPLEMENTATION_STATUS.md)을 연결했다. 아래 내용은 제품 개발 착수 당시의 검토다. 운영 배포·개인화·피드백은 남아 있다.

## 결론과 권장 선택

핵심 앱을 만들 수 있는 구조다. 가장 큰 불확실성은 화면 개수가 아니라 **아바타 착장 확장 비용과 추천 효과**다. 전신 렌더 이미지의 전환은 실제 Android에서 검증했고, 실시간 3D·자유 의상 조합은 아직 검증하지 않았다.

| 영역 | 권장안 | 결정·검증 수준 |
|---|---|---|
| 앱 | 기존 Kotlin + Jetpack Compose 유지 | 기존 골격·디버그 자산 표시 빌드 확인 |
| 아바타 | 승인한 3D 토이 스타일의 완성 착장 이미지 전환부터 시작 | 겉옷 OFF/ON 한 쌍의 실제 기기 표시 확인. 전체 외형/의상 확장은 미정 |
| 날씨 | 국내용 기상청 단기/초단기 계열 | 후속 작업에서 마포구·강남구 실제 응답 확인. 보조 API는 미연동 |
| 추천 | 앱 내부의 버전 있는 규칙과 의류 카탈로그 | 제안. 기온/활동/민감도 적용과 효과 검증 전 |
| 개인 기록 | DataStore에 설정, Room 계열에 기록·관계 데이터 | 공식 기능에 근거한 제안. 라이브러리 추가·버전 선택 전 |
| 서버 | 날씨 키 보호·공용 캐시·응답 정규화에 한정한 작은 서버 | 로컬 FastAPI 구현·HTTP 확인. 운영 호스팅/배포 전 |
| 계정 | 초기에는 계정 없이 기기 내 사용 | 기존 기획 유지. Supabase 계정/동기화는 첫 기능의 전제 아님 |

추천 계산과 개인 체감 기록은 앱에서 처리하고, 날씨 서버에는 집/직장이라는 역할·신체 정보·피드백 원문을 보내지 않는 구조를 권장한다. 서버는 필요한 지역 식별자/좌표와 시간 범위로 조회한다. 이것이 개인정보가 전혀 전송되지 않는다는 의미는 아니며, 서버에 전송되는 요청 정보는 실제 구현에 맞게 명시해야 한다.

## 실제 수행한 아바타 검증

승인 홈의 캐릭터를 참조해 내장 Imagegen으로 긴팔·긴바지 자산과 재킷 착용 자산을 만들었다. 모두 1024×1536 RGBA PNG이며 투명 배경을 포함한다. 처음 결과의 가장자리 처리를 재요청한 뒤 Android에서 밝은/어두운 배경으로 확인했다. 상세 수치는 [자산 매니페스트](../design/avatar-validation-manifest.json)에 기록했다.

- [겉옷 없음](../app/src/debug/res/drawable-nodpi/avatar_validation_long.png), [재킷 착용](../app/src/debug/res/drawable-nodpi/avatar_validation_jacket.png): 약 1.5MB씩. 해상도와 인물의 발·머리 정렬이 비슷한 한 쌍.
- API 37 PCRS 에뮬레이터에서 전환·240/320dp 높이·96dp 미리보기·밝은/어두운 배경을 확인했다. 320dp 폭에서도 줄 바꿈/스크롤로 접근 가능함을 확인했다.
- PNG의 alpha≥128 실루엣 경계는 OFF `[286,52,725,1462]`, ON `[287,52,730,1463]`이다. 경계가 비슷한 것은 얼굴/픽셀이 완전히 같다는 증명은 아니다. 손·표정·외곽의 미세한 변화는 추가 아트 검수가 필요하다.
- `assembleDebug`, `lintDebug`, `assembleRelease` 성공. lint 오류 0, 기존 유형 경고 8. 디버그 이미지와 검증 Activity는 릴리스에 포함되지 않는다.
- 에뮬레이터 부팅 직후 System UI 응답 지연 대화상자가 한 번 나타났고 대기 후 해소했다. 이후 검증 화면을 확인했다. 저사양 성능·앱 ANR/메모리·장시간 전환을 정량 검증한 결과는 아니다.

현재 결과는 **완성 이미지를 넣어 옷 상태를 바꾸는 기능이 가능한지**의 검증이다. 자유로운 상하의 조합·다양한 체형·헤어·피부 톤·애니메이션·실시간 3D를 검증한 것으로 확대하지 않는다. PNG의 RGB 미리보기에는 배경색처럼 보이는 영역이 있어도 실제 표시에는 alpha가 적용된다. 가장자리 품질은 최종 제품 자산 제작에서 다시 확인한다.

코드는 [디버그 검증 Activity](../app/src/debug/java/com/pcrs/thermalguide/validation/AvatarValidationActivity.kt)에만 추가했다. 기존 홈과 앱의 기본 진입은 빈 골격을 유지한다. 이번 변경은 핵심 앱 화면 전체 구현이 아니다.

## 서버와 기존 코드의 처리

기존 FastAPI는 프레임워크 선택의 참고로만 사용하고 새 날씨 어댑터/정규화/캐시 경계를 작게 분리하는 것을 권장한다. 기존 Supabase·전체 인증·옷장·추천 DB에 종속된 엔드포인트를 앱의 첫 요청으로 삼지 않는다. 기존 서비스나 데이터는 삭제하지 않는다.

확인한 근거:

- `backend/weather_client.py`에는 조회/캐시 모두 실패 시 `fallback_mock` 예보 생성, 대기질 실패 시 고정 수치 채움, 만료 캐시 반환이 있다. 새 실제 데이터 경로로 그대로 가져오지 않는다.
- `backend/main.py`에는 나이·성별·체지방률 기반 보정과 UTCI→의류 보온량 매핑이 있다. 새 사용자 입력 범위와 다르고 효과를 검증하지 않았으므로 기존 개인화 수식을 곧바로 재사용하지 않는다.
- 기존 피드백 요청은 현재 설계의 강도·겉옷 휴대·실제 착장·환경·예보 불일치를 충분히 표현하지 않는다. 새 데이터 계약이 필요하다.

서버가 맡을 일은 외부 키 보관, 지역/시간별 요청 합치기, 이용 한도 방어, 공급자 오류 정규화다. 호출량은 사용자 수가 아니라 캐시 재사용·지역·갱신 주기에 따라 산정한다. 예를 들어 단순 가정으로 1,000명×2지역×하루2회×30일은 월12만 요청이다. 이것은 운영량 예상이 아닌 계산 예시이며 공용 캐시/서비스별 실제 호출 수를 반영해 다시 계산해야 한다.

호스팅은 아직 선택하지 않았다. 무료 배포의 가능성과 아침 알림 시점에 응답 가능한 운영 구조를 같은 것으로 보지 않는다. 기존 Render/Vercel은 이번에 변경하지 않았다.

## 추천과 개인 보정의 첫 구현

외부 LLM이 매번 의상을 만들어내는 구조보다, 카탈로그·규칙·근거 코드를 가진 결정 로직을 먼저 구현하는 것을 권장한다. 입력이 같으면 결과와 설명이 재현되어야 하고, 착장 자산이 없다는 이유로 다른 두께의 옷을 추천하면 안 된다.

1. 지역·대상 날짜/시각과 자료 유효성을 확인한다.
2. 두 출발 시점의 기온·바람·강수 등 지원 자료를 표준 단위로 정규화한다.
3. 기본 의류 범주/두께·겉옷 탈착 후보를 만든다. 이동·민감도는 입력된 것만 적용한다.
4. 적합한 대안을 순위화하고 종류/두께와 선택 이유 코드를 함께 반환한다.
5. 표현 가능한 자산이 있으면 연결한다. 없으면 의류 그림·범주로 표시하며 임의의 잘못된 아바타를 쓰지 않는다.
6. 실제 착장 확인이 있는 피드백을 유사한 환경별 보정 후보로 사용한다. 강한 한 번의 답으로 모든 추천을 바꾸지 않는다.

습도/바람/도보가 몇 도에 해당하는지, 신체값이 정확도에 기여하는지 임의로 정하지 않는다. 의류 보온량이나 체감온도 점수로 정밀하게 보이게 하기 전에 근거와 사용자 검증이 필요하다. 추천 경계·보정 폭·최소 표본은 버전 있는 조정값으로 설계하고 지금 확정 수치로 만들지 않는다.

데이터 경계는 [개발용 계약 초안](DEVELOPMENT_CONTRACTS.md)에 적었다. Room과 DataStore의 역할 구분은 [Android Room 안내](https://developer.android.com/training/data-storage/room), [DataStore 안내](https://developer.android.com/topic/libraries/architecture/datastore)에 근거한다. 아직 의존성을 추가하거나 버전을 확정하지 않았다.

## 다음 제품 개발 단위

1. 완료한 기반: API 키 설정, 두 지역 실제 응답, 지역 검색·시점·필수 변수·오류·캐시와 로컬 HTTP 검증. 세부 결과는 날씨 연동 기록을 따른다.
2. 승인한 시안의 홈을 Compose로 옮긴다. 이번 검증 이미지가 최종 자산이 아님을 유지하고 종류·두께 데이터와 연결한다.
3. 기본 추천과 대안·후보 저장을 연결한 뒤 실제 착장/피드백 저장을 추가한다.

최신 주요 화면의 검토는 사용자가 완료했다. 별도 화면 이동 프로토타입을 필수 선행 단계로 더 만들지 않고 필요한 부분은 Android에서 기능 단위로 확인한다. 제공자 계약/계정, 자산 최종 품질, 추천 효과와 실제 앱 전체 디자인의 완성도는 남은 작업이다.
