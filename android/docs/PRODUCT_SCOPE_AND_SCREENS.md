작성일: 2026-11-01. [인터뷰 기록](PRODUCT_PLANNING.md)을 바탕으로 한 **검토용 초안**입니다. 아래 화면과 동작은 구현 완료를 의미하지 않습니다.

후속 검토: 글 중심 구성에 대한 사용자 의견을 반영해 [날씨 앱 벤치마킹과 v0.4 UX 방향](WEATHER_UX_BENCHMARK.md)을 작성했습니다. v0.3은 기능·흐름 참조용이며, 시각적 구성은 재검토 중입니다.

최신 Figma: [전체 사용 흐름 v0.3](https://www.figma.com/design/OcCbCtozsgYiLG5iUXxgnw?node-id=17-1070). [화면 21개와 상세 흐름·검수 상태](SCREEN_FLOW_V0_3.md)를 함께 봅니다. v0.1·v0.2 페이지는 비교용으로 보존합니다.

v0.3은 간소화된 초기 진입을 유지하고 시간별·추천 이유·선택 설정·상세 피드백·예외 상태로 확장했습니다. 대표 화면 21개와 이동 컨트롤 65개를 생성했습니다. 생성 후 MCP 한도에 도달해 마지막 문구 정리·전체 재검수는 남아 있으며, 정확한 완료 범위는 상세 문서에 기록했습니다.

이전 v0.2 산출물: 첫 실행·기본 추천·출퇴근 설정·맞춤 추천의 4개 화면과 6개 이동 연결. v0.1의 대표 화면 12개와 31개 연결도 보존했습니다. 두 이전 버전은 편집 가능한 요소로 구성하고 전체 배치·폰트·연결 대상을 검수했습니다. 모든 버전은 실제 날씨·추천 계산과 저장을 구현하지 않은 흐름 검토용 초안입니다.

## 0. 초기 입력량에 따른 변경안

사용자 의견: 첫 실행 후 입력량이 너무 많음. 이를 반영해 추천을 보기 전 4단계 설정을 **지역 한 곳 선택 → 기본 추천**으로 축소하는 안을 제안합니다.

| 시점 | 요청하는 정보 |
|---|---|
| 처음 앱 실행 | 기준 지역 한 곳. 직접 검색 또는 선택적으로 현재 위치 사용 |
| 기본 추천을 본 후 ‘내 출퇴근에 맞추기’ 선택 | 집·출발 지역, 직장·학교 지역, 출근·귀가 시각. 먼저 고른 지역을 재사용하고 수정 가능 |
| 더 세밀하게 조정하고 싶을 때 | 도보 시간·교통수단·실내 환경·민감도 |
| 사용자가 원할 때만 | 키·몸무게 등 선택 신체 정보, 아침 알림 설정 |

첫 추천은 선택한 지역의 아침·저녁 예보를 기준으로 한 **기본 추천**임을 표시합니다. 두 장소·출퇴근 시각이나 민감도를 입력하기 전에 해당 정보를 알고 있는 것처럼 개인화 결과를 표시하지 않습니다. 미입력된 이동 방식·실내 환경을 사실처럼 저장하지 않습니다.

이 변경안은 v0.3에서도 유지합니다. 아래 O1~O4는 v0.1 화면 참조이며, 첫 실행에 모두 강제하는 흐름은 대체합니다. 선택 신체 정보 자체를 제거하는 결정은 아닙니다.

## 1. 제품의 한 문장 정의

출근·등교하는 사람이 생활 패턴과 개인 체감을 바탕으로, 출근부터 귀가까지 입을 기본 차림을 아침에 결정하도록 돕는 Android 날씨 앱.

핵심 결과는 상의·하의·겉옷의 종류와 두께 수준, 시간대별 탈착 방법입니다. 색상·스타일 코디나 실제 보유 의류의 자동 선택은 현재 핵심 범위로 확정하지 않습니다.

## 2. 첫 버전 범위 제안

| 기능 | 포함할 범위 | 근거·상태 |
|---|---|---|
| 위치 | 대한민국의 집과 직장·학교 두 장소 저장·수정 | 인터뷰 확인 |
| 생활 패턴 | 출근·귀가 시각, 이용 요일, 도보 시간, 교통수단, 도착 후 환경 | 최초 설정 후 자동 추천 선호 반영. 상세 입력 방식은 제안 |
| 개인화 설정 | 더위·추위 민감도, 선택 키·몸무게 | 인터뷰 확인. 신체 항목의 계산 기여는 검증 필요 |
| 날씨 | 두 장소와 출근·귀가 시간대의 기온·습도·바람·강수 등 추천 입력 | 필요한 항목·제공자·관측 자료 지원 여부를 개발 명세에서 확정 |
| 오늘의 차림 | 상의·하의·겉옷과 두 시간대 대응법, 추천 이유 | 인터뷰 확인 |
| 준비물 | 강수 등에 따른 우산 등 짧은 안내 | 핵심 추천에 부가하는 제안 |
| 시간별 확인 | 집·직장별 시간대 예보와 출근·귀가 구간 확인 | 추천 근거를 이해하는 보조 기능으로 제안. 운동 점수·다일 계획은 보류 |
| 아침 알림 | 선택한 시간·요일에 복장 요약, 눌러 오늘 추천 열기 | 사용자가 제안한 기능을 첫 버전 후보에 포함. 정확한 시각 보장·갱신 방식은 기술 검토 |
| 체감 피드백 | 홈에서 자발적 입력. 적당하면 간단히 완료, 불편하면 강도·시간·상황·실제 착장을 선택 | 인터뷰 확인. 피드백 요청 알림 없음 |
| 개인 보정 | 유사한 시간·활동·환경에서 제한적으로 조정 | 구현 제안. 효과를 검증하며 한 번의 경험을 모든 조건에 확장하지 않음 |
| 설정·데이터 | 장소·패턴·민감도·알림 수정, 피드백 보정 초기화 | 지속 사용과 사용자 제어를 위한 제안 |

초기 사용은 계정 없이 시작하고 기기에 설정을 저장하는 방식을 제안합니다. 로그인·클라우드 동기화 여부는 별도 결정이며, 기존 Supabase 재사용을 전제로 화면을 고정하지 않습니다.

## 3. 보류·후속 검토

개인 옷장과 의류 사진 인식, 실제 옷의 스타일 코디, 러닝·운동 추천, 경로 추적·지하철 혼잡도, 실내 온도 자동 수집, 해외 지역, 가족 계정, 위젯, 광고·구독은 이번 와이어프레임의 핵심 흐름에서 보류합니다. 기존 빈 앱의 옷장 탭을 유지하는 것으로 해석하지 않습니다.

광고는 향후 AdMob 통합을 고려하고 날씨 API의 상업적 이용 조건을 제공자 선정 시 확인합니다. 초기 와이어프레임에 광고 자리를 고정하지 않습니다.

## 4. 정보 구조와 화면 목록

하단 탭 제안: **오늘 / 시간별 / 설정**. 피드백은 오늘 추천에서 열고 별도 탭으로 만들지 않습니다. 최초 진입은 지역 한 곳만 선택하고 추천을 표시하며, 추가 설정은 관련 기능을 사용할 때 요청합니다.

v0.1의 아래 화면 목록은 상세 기능의 참조용입니다. 초기 진입 순서는 §0 및 §5의 v0.2 흐름을 우선합니다.

|---|---|---|---|
| O1 | 생활권 설정 | 집과 직장·학교를 지정. 주소·장소 검색과 선택 상태 | O2 |

## 5. 핵심 흐름

처음 사용(v0.2): I1 지역 한 곳 선택 → H0 지역 기준 기본 추천.

출퇴근 맞춤 시작(v0.2, 선택): H0 → C1 두 장소·출퇴근 시각 → H2 출퇴근 기준 추천. C1에서 나중에를 선택하면 H0으로 돌아갑니다.

민감도·이동 상세·신체 정보·아침 알림은 각각 설정에서 필요할 때 추가합니다. v0.1의 O1 → O2 → O3 → O4 전체 안내를 첫 추천 전에 요구하지 않습니다.

아침 사용(v0.3): 오늘 추천 H0 또는 H2 → 해당 상태의 추천 이유 R0 또는 R2, 시간별 W0 또는 W2. 선택적 아침 알림도 저장된 상태의 오늘 추천을 여는 방향으로 설계합니다.

착용 후(v0.3): H0/H2 위에서 F1 열기 → 적당하면 F3, 더움은 FH, 추움은 FC, 다른 착장은 FA → F3. 닫으면 원래 추천 화면으로 복귀하는 오버레이 흐름입니다.

설정 수정(v0.3): S0/S2 → 체감 P1·이동 상세 M1·알림 N1 → 진입 화면으로 복귀. 출퇴근 C1은 ‘저장하고 추천 보기’로 H2에 진입합니다. 최초 설정 전체를 다시 강제하지 않습니다. 실제 입력 보존·검증은 상세 설계에서 보완합니다.

## 6. 홈 정보 우선순위 제안

1. 오늘의 한 줄 안내와 상의·하의·겉옷.
2. 출근·귀가의 날씨 차이와 겉옷 탈착 방법.
3. 우산 등 준비물과 추천 이유 진입.
4. 실제 착용 후 피드백 진입.
5. 위치·기상 데이터 갱신 시각과 출처.

기상 수치 전체를 홈 상단에 크게 나열하기보다 착장 결정을 먼저 돕습니다. 날짜·시간·날씨·개인 정보 예시는 와이어프레임용 가상 데이터로 구분합니다.

## 7. 피드백의 필수 해석 규칙

추천 수락과 실제 착용 후의 편안함은 별개입니다. ‘추천대로 입었고 적당했어요’는 실제 경험한 경우에만 선택하게 표현합니다.

상세 피드백 후보는 더위·추위 3단계 강도, 당시 시각·구간, 땀·후텁지근함·햇볕·바람·비·대중교통·실내 냉방 등 상황입니다. 강도는 주관적 척도이며 수치 측정으로 표현하지 않습니다. 실제 착장 변경을 확인하며 전체 옷장 등록을 요구하지 않습니다.

추천 당시 예보 스냅샷과 시간·위치·추천 규칙을 연결합니다. 사용자의 ‘습했다’ 응답을 관측 습도나 예보 오류의 확정값으로 사용하지 않습니다. 실제 관측 비교가 가능하지 않으면 비교 자료 없음으로 구분합니다. 상세 관측 API 지원 여부는 제공자 선정 때 확인합니다.

## 8. 디자인·개발 진행 방식

1. **기능·화면 초안:** 이 문서에서 범위·우선순위·미결정을 구분.
2. **Figma 저해상도 와이어프레임:** 편집 가능한 화면과 연결로 배치·문구·입력량 검토. 시각 스타일 확정 전 단계.
3. **사용 흐름 검토:** 첫 설정, 아침 추천, 불편했던 날의 피드백, 실패·권한 거절 흐름을 확인하고 수정.
4. **UI 디자인:** 색상·타이포·아이콘·공통 컴포넌트와 상태를 확정.
5. **개발 명세:** 화면별 입력 검증, 데이터·API, 추천·보정 규칙, 알림 처리, 완료 기준 확정.
6. **구현·검증:** 확정된 화면부터 Android 코드 구현과 에뮬레이터 검증.

다음 단계로 넘어가기 전에 검토할 결과물을 제시합니다. 기능·화면이 바뀌면 먼저 문서와 Figma를 갱신합니다.

## 9. 와이어프레임 검토 기준

- 아침에 추가 입력 없이 차림을 결정할 수 있는가?
