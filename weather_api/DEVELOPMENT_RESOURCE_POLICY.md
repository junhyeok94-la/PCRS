# 백엔드 자원 사용 원칙

사용자 요청에 따라 이후 구현에서도 아래 원칙을 적용한다. 최적화 효과는 테스트와 요청 집계로 확인하며 구현하지 않은 분산 운영 능력을 주장하지 않는다.

1. **필요한 지역만 수집한다.** 사용자 요청이 없는 전국 격자 선조회·상시 폴링을 기본으로 추가하지 않는다.
2. **원천 자료와 개인 추천을 분리한다.** 같은 제공자·격자·발표 자료는 공유한다. 프로필 변경·탭 이동·아바타 선택은 캐시된 날씨로 로컬 재계산한다.
3. **재시작과 동시 요청도 고려한다.** 영속 캐시, 요청 합치기, 상류 동시 수집 상한, 실패 간격 증가를 함께 사용한다.
4. **모든 저장에 상한을 둔다.** 캐시 레코드 수·payload 용량·실패 키·요청 제한 맵·날짜별 집계 보존 기간을 제한한다. SQLite 실제 파일 크기와 WAL의 운영 한계는 별도로 확인한다.
5. **실제 HTTP 시도를 센다.** 페이지·실패·재시도를 포함한다. 승인량이 확인되면 여유 있는 자체 상한을 설정한다. 계정 전체 사용량과 이 서비스의 집계를 혼동하지 않는다.
6. **실패를 숨기지 않는다.** 출처와 시각을 보존하고, 제한된 이전 자료를 표시한다. 오류 응답·디스크 읽기를 최신 데이터 취득으로 취급하지 않는다.
7. **작은 운영 구조로 시작한다.** 현재는 단일 호스트 SQLite와 제한된 메모리 캐시를 사용한다. 측정된 필요가 생기면 공유 캐시·전역 카운터·분산 락을 도입한다. 무료 호스팅의 임시 저장소를 영속 저장소로 가정하지 않는다.
8. **비용을 늘리는 기능은 별도로 검토한다.** 사용자별 외부 AI 생성, 매일 콘텐츠 수집·생성, 광고/알림 작업도 캐시·실행 빈도·실패 시 대안을 정하고 추가한다.

현재 구현·검증·제약: [캐시 결과](../android/docs/CACHE_IMPLEMENTATION_STATUS.md). 운세 콘텐츠는 [기획 후보](../android/docs/PRODUCT_IDEA_BACKLOG.md)이며 백엔드 작업이나 출생정보 수집을 아직 추가하지 않았다.
